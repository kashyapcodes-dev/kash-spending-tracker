# M1: Core rebuild on Postgres, Drizzle and Better Auth

- **Status:** Not started
- **Depends on:** M0
- **ADRs:** [0001](../../adr/0001-foundational-decisions.md), [0002](../../adr/0002-transactions-table.md)

## Goal

Everything the original app does, rebuilt on the new stack with authorization in application code: sign up, get a budget, manage categories, record expenses and incomes (now with edit and delete), import a CSV, see the dashboard and compare two periods. All through `/api/v1`, described by a generated OpenAPI document, and covered by an authz test for every endpoint.

## Scope

1. Drizzle schema, migrations and seed in `packages/db`.
2. Better Auth with email and password: sign up, sign in, sign out, password reset.
3. Service layer in `packages/core` with mandatory budget-scope authorization.
4. `/api/v1` endpoints listed below, with zod contracts in `packages/contract`, a generated OpenAPI document, and a generated typed client in `packages/api-client`.
5. Web UI: auth pages, dashboard, categories, expenses, incomes, compare report, budget switcher.
6. A budget is created automatically on signup.
7. Ported logic (see [Ported logic](#ported-logic)).
8. Test infrastructure: a real Postgres for API tests, test factories, and the authz matrix.

## Non-scope

- Invites and member management UI (M4). The `budget_members` table and role checks exist now; only the owner row is ever created in M1.
- Column-mapping wizard and saved presets UI (M5). M1 ships built-in presets only.
- Docker packaging (M2), data migration (M3), PWA (M4), bank sync (M5), configurable dashboards (M6), AI (M7).
- Social login, two-factor auth, email verification as a hard gate.
- Multi-currency within a budget.

## Data model changes

Auth tables (`user`, `session`, `account`, `verification`) are generated by Better Auth's Drizzle adapter and committed as part of the schema. Domain tables:

```
budgets
  id          uuid pk
  name        text not null                      -- 2 to 200 chars
  currency    text not null default 'USD'        -- ISO 4217
  created_by  text null references user(id) on delete set null
  created_at, updated_at  timestamptz

budget_members
  budget_id   uuid not null references budgets(id) on delete cascade
  user_id     text not null references user(id) on delete cascade
  role        enum('owner','editor','viewer') not null
  created_at  timestamptz
  primary key (budget_id, user_id)
  index (user_id)

categories
  id          uuid pk
  budget_id   uuid not null references budgets(id) on delete cascade
  name        text not null                      -- 2 to 200 chars
  is_active   boolean not null default true
  created_at, updated_at  timestamptz
  unique (budget_id, lower(name))

transactions            -- exactly as in ADR-0002

import_presets
  id          uuid pk
  budget_id   uuid not null references budgets(id) on delete cascade
  name        text not null
  mapping     jsonb not null                     -- shape defined in M5
  created_at, updated_at  timestamptz
```

`import_presets` is created now so M5 needs no restructuring; nothing reads or writes it in M1.

Rules:

- A budget always has at least one owner. The last owner cannot be removed or demoted.
- Deleting a category sets `category_id` to null on its transactions.
- Deleting a budget cascades to its members, categories, transactions and presets.
- Seed (`pnpm db:seed`, development only): two users, two budgets, a handful of categories and about 200 transactions over six months, so the dashboard and compare report have something to show.

## Authorization model

All of this lives in `packages/core/authz` and is the only way to reach data.

- **Actor.** `{ userId }` resolved from the Better Auth session in the route handler. No session: `401`.
- **Budget access.** `requireBudgetRole(actor, budgetId, minRole)` loads the membership row. Not a member (or the budget does not exist): `404 not_found`, so existence is not revealed. Member with a lower role than needed: `403 forbidden`.
- **Role order.** `viewer` < `editor` < `owner`. Viewer: read. Editor: read and write categories and transactions. Owner: everything, including renaming and deleting the budget.
- **Child resources.** A category or transaction is always loaded with `WHERE id = ? AND budget_id = ?` using the budget ID from the path, after the membership check. An ID that belongs to another budget gives `404`. A `categoryId` in a request body is checked to belong to the path's budget; otherwise `422`.
- **Service signatures.** Every exported service function takes `(actor, budgetId, ...)` and calls `requireBudgetRole` first. A unit test enumerates the exports of the service modules and fails if a function with data access does not go through the authz helper (implemented by having data access only available from a context object that `requireBudgetRole` returns).
- Route handlers contain no Drizzle imports (lint rule).

## API endpoints

Conventions:

- JSON in and out. Field names are camelCase. Money is `amountCents` (integer). Dates are `YYYY-MM-DD`.
- Errors: `{ "error": { "code": string, "message": string, "details"?: unknown } }` with codes `unauthenticated` (401), `forbidden` (403), `not_found` (404), `validation_failed` (422, `details` holds zod issues), `conflict` (409), `internal` (500). The original app's `307` with a `redirect_url` body is not carried over.
- List endpoints use cursor pagination: `?limit=` (default 50, max 200) and `?cursor=`, returning `{ "items": [...], "nextCursor": string | null }`.
- Authentication is the Better Auth session cookie. Better Auth's own routes are mounted at `/api/auth/*` and are not part of the versioned contract.
- State-changing requests are protected against cross-site request forgery (same-site cookies plus an origin check).

"Authz" below gives the minimum role, as enforced by `requireBudgetRole`. "Member" means any role.

| Method | Path | Purpose | Authz |
|---|---|---|---|
| GET | `/api/v1/health` | Liveness (from M0) | Public |
| GET | `/api/v1/openapi.json` | Generated OpenAPI 3.1 document | Public |
| GET | `/api/v1/me` | Current user `{ id, email, name }` and their budgets with role | Authenticated; returns only the caller's own data |
| GET | `/api/v1/budgets` | List budgets the caller belongs to | Authenticated; filtered to the caller's memberships |
| POST | `/api/v1/budgets` | Create a budget `{ name, currency? }`; the caller becomes owner | Authenticated |
| GET | `/api/v1/budgets/{budgetId}` | Get one budget with the caller's role | Member |
| PATCH | `/api/v1/budgets/{budgetId}` | Rename or change currency | Owner |
| DELETE | `/api/v1/budgets/{budgetId}` | Delete the budget and all its data. Refused with `409` if it is the caller's only budget. | Owner |
| GET | `/api/v1/budgets/{budgetId}/categories` | List categories; optional `?active=` filter (`true` or `false`); each has `transactionCount` | Member |
| POST | `/api/v1/budgets/{budgetId}/categories` | Create `{ name }`; `409` on duplicate name | Editor |
| PATCH | `/api/v1/budgets/{budgetId}/categories/{categoryId}` | Update `{ name?, isActive? }` | Editor; category must belong to the budget |
| DELETE | `/api/v1/budgets/{budgetId}/categories/{categoryId}` | Delete; its transactions become uncategorised | Editor; category must belong to the budget |
| GET | `/api/v1/budgets/{budgetId}/transactions` | List; filters `type`, `from`, `to`, `categoryId` (`none` for uncategorised), `q` (name contains); sorted by date descending then created time | Member |
| POST | `/api/v1/budgets/{budgetId}/transactions` | Create one or many: `{ items: [{ type, name, amountCents, date, categoryId?, notes? }] }`, 1 to 500 items, all-or-nothing in one database transaction | Editor; every `categoryId` must belong to the budget |
| GET | `/api/v1/budgets/{budgetId}/transactions/{transactionId}` | Get one | Member; transaction must belong to the budget |
| PATCH | `/api/v1/budgets/{budgetId}/transactions/{transactionId}` | Update any of `type, name, amountCents, date, categoryId, notes` | Editor; transaction and any new `categoryId` must belong to the budget |
| DELETE | `/api/v1/budgets/{budgetId}/transactions/{transactionId}` | Delete | Editor; transaction must belong to the budget |
| GET | `/api/v1/budgets/{budgetId}/reports/summary` | Dashboard data for `?from=&to=` and optional `excludeCategoryIds=` (comma-separated) | Member |
| GET | `/api/v1/budgets/{budgetId}/reports/compare` | Two-period comparison for `?aFrom=&aTo=&bFrom=&bTo=` | Member |
| POST | `/api/v1/budgets/{budgetId}/imports/csv/preview` | Parse an uploaded CSV (multipart, max 5 MB) and return candidate transactions and issues. Writes nothing. | Editor |

Differences from the original that fix its authorization gaps: the dashboard query is scoped to a budget (the original filtered by date only); category update is scoped to a budget (the original updated by ID only); creates take the budget from the path after a membership check (the original trusted `budget_id` in the body); the compare report requires an explicit budget (the original fell back to the user's first).

### Report shapes

`reports/summary` (ported from the original dashboard's client-side aggregation; now computed on the server):

```jsonc
{
  "range": { "from": "2026-11-01", "to": "2026-11-11", "days": 11 },
  "totals": {
    "incomeCents": 500000, "expenseCents": 123456, "netCents": 376544,
    "expenseCount": 42, "excludedExpenseCount": 3,
    "avgExpensePerDayCents": 11223
  },
  "categories": [   // only categories with at least one expense in range, by total descending
    { "categoryId": "<uuid>|null", "name": "Groceries", "totalCents": 43210, "expenseCount": 12, "excluded": false }
  ]
}
```

Excluded categories (the original's per-category filter toggle) are left out of `totals` but still listed in `categories` with `excluded: true`. The expense rows under the dashboard come from the transactions list endpoint with the same range.

`reports/compare` (ported from the original `summarizePeriod` and `compareCategorySummaries`): for each of period A and B, `range`, `totals` (`incomeCents`, `expenseCents`, `netCents`, `incomeCount`, `expenseCount`, `avgExpenseCents`, `avgIncomeCents`, `avgExpensePerDayCents`, `days`), `categorySummary` (per category: total, count, average; uncategorised as its own row; by total descending) and `topExpenses` (ten largest). Then `comparison.totalsDelta` (B minus A for each total, and `expensePct` as a fraction, `null` when A is zero) and `comparison.categories` (union of both periods' categories with `periodA`, `periodB` and `delta` including `totalPct`, sorted by absolute change in total descending).

## Ported logic

Port these into `packages/core` as pure, unit-tested TypeScript. Keep the behaviour; change only what this spec says.

| Original | New home | Notes |
|---|---|---|
| `parseMoney` (CSV import) | `core/money` | Returns integer cents from the string without floats. Handles `$`, commas, spaces, parentheses and leading minus. |
| `parseCsvDate` | `core/import` | Accepts `MM/dd/yyyy`, `M/d/yyyy`, `MM/dd/yy`, `M/d/yy`, `yyyy-MM-dd`, then ISO. Returns `YYYY-MM-DD`. |
| `normalizeForMatch`, `buildTokenOrderRegex`, `findMatchingExpense` | `core/import/categorize` | Fuzzy auto-categorise: normalise names (lowercase, strip diacritics and punctuation), exact match first, then tokens in order, preferring the longest matching existing name. Only suggest a category that is active. Matches against the budget's existing expense transactions. |
| Row validation (`validateAndNormalizeExpense`) | `core/import` | Errors for missing name, invalid amount, invalid date. Non-positive amounts are skipped with a warning. Issues carry `level`, `row`, `name`, `field`, `message`. |
| CSV shape detection | `core/import/presets` | The three hard-coded parsers become declarative built-in presets (data, not code): `debit-credit` (Description, Transaction Date, Debit, Credit), `single-amount` (Description, Date, Amount) and `withdrawals-deposits` (Description, Date, Withdrawals, Deposits). Detection picks the first preset whose columns are all present. No preset is named after a person. |
| `summarizePeriod`, `compareCategorySummaries`, inclusive day count | `core/reports` | As described above. |
| Dashboard aggregation | `core/reports` | Server-side. Per-day average uses the inclusive day count (fixes the original's divide-by-zero on a one-day range). |

Import flow, unchanged from the original in shape: the preview endpoint returns `{ candidates: [{ name, amountCents, date, suggestedCategoryId | null }], issues: [...] }`. The UI loads the candidates into the multi-row expense form for the user to fix and categorise, and submitting the form calls the bulk create endpoint. Status codes: `200` with candidates (issues may be present), `422` when no row could be parsed.

## UI

Port the existing screens to TypeScript using the generated API client. Keep the current look (shadcn, recharts). No starter-template leftovers (deploy button, logos, environment warnings).

- **Auth:** sign up, sign in, forgot password, reset password. After signup the user lands on the dashboard of an automatically created budget named "My Budget". Password reset works end to end: the emailed link opens a reset page that exists and accepts a new password (the original redirected to a page that did not exist). When no SMTP is configured, the reset link is written to the server log, and the page says so.
- **Route protection:** every page except the auth pages and the landing page requires a session; otherwise redirect to sign in. (The original guarded only the dashboard.)
- **Budget switcher** in the header: lists the user's budgets, switches the current one, and offers "New budget". The current budget is in the URL (`/b/{budgetId}/dashboard`), so links are shareable and nothing uses "the first budget".
- **Dashboard:** date range picker defaulting to the current month to date; cards for total income, total expenses with per-day average, expense count with excluded count, and net; category breakdown pie; category list with a toggle to exclude a category from totals; expenses table. Data loads on open and when the range changes (the original needed a button press).
- **Categories:** list with transaction counts, add, rename, activate or deactivate, delete with confirmation. Inactive categories are not offered when entering expenses.
- **Expenses:** multi-row entry form (name, amount, date, category) with add row, remove row and submit; "Import CSV" fills the form from the preview endpoint and shows row issues; below it, a table of expenses with edit and delete.
- **Incomes:** entry form and a table with edit and delete.
- **Compare:** two date ranges, totals with deltas, per-category comparison table, top expenses for each period.
- Amount inputs accept what a person types (`12.50`, `$1,200`) and convert with the shared money parser. Viewers see no write controls.

## Acceptance tests

API tests run with Vitest against a real Postgres (a service container in CI, Testcontainers or a local database in development), calling route handlers with a session for a factory-made user.

### Authz matrix (mandatory, generated from a table of endpoints)

For every endpoint in the table above that has a `{budgetId}`:

- `M1-AZ-1` No session → `401 unauthenticated`.
- `M1-AZ-2` User A, a member of budget A only, calls the endpoint on budget B → `404 not_found`, and budget B's data is unchanged.
- `M1-AZ-3` A viewer calls an endpoint whose minimum role is editor or owner → `403 forbidden`, and nothing changes.
- `M1-AZ-4` An editor calls an owner-only endpoint → `403 forbidden`.
- `M1-AZ-5` For endpoints with a child ID: an editor of budget A uses budget A in the path with a category or transaction ID from budget B → `404`, and the budget B row is unchanged.
- `M1-AZ-6` Create or update a transaction in budget A with a `categoryId` from budget B → `422`, nothing written.
- `M1-AZ-7` A meta-test fails if an endpoint exists in the OpenAPI document but has no row in the authz test table.
- `M1-AZ-8` `GET /budgets` and `GET /me` for user A never include budget B.

### API behaviour (Vitest)

- `M1-API-1` Signup creates a user, a budget named "My Budget" and an owner membership, in one transaction.
- `M1-API-2` Transactions: create one; create 500 in bulk; a bulk request with one invalid item writes none and returns `422` with the item index.
- `M1-API-3` Transactions: update each field; delete; list filters by type, date range (inclusive both ends), category, uncategorised and name; pagination returns every row exactly once.
- `M1-API-4` `amountCents` of 0, negative, non-integer or above the maximum → `422`.
- `M1-API-5` Categories: duplicate name (case-insensitive) → `409`; delete sets transactions' category to null; deactivate keeps transactions.
- `M1-API-6` Budgets: deleting the caller's only budget → `409`; deleting another removes all its rows.
- `M1-API-7` `reports/summary` matches hand-computed totals for a fixture, including excluded categories and a one-day range (per-day average equals the total).
- `M1-API-8` `reports/compare` matches a fixture: totals, deltas, percentage `null` when period A is zero, category union, uncategorised row, top ten.
- `M1-API-9` CSV preview: one fixture file per built-in preset produces the expected candidates; credits, deposits and non-positive amounts are skipped with warnings; unknown columns → `422`; a file over 5 MB → `413`.
- `M1-API-10` The OpenAPI document validates as OpenAPI 3.1, lists every route, and a contract test checks each response in these tests against its schema.

### Unit (Vitest, `packages/core`)

- `M1-U-1` Money parser table: `"12.50"`→1250, `"$1,234.56"`→123456, `"(5.00)"`→-500, `"-3"`→-300, `"0.1"`→10, `"1.005"`→null (more decimal places than the currency has is rejected, not rounded), `""`→null, `"abc"`→null. No test value goes through a float.
- `M1-U-2` Date parser: each accepted format; `02/30/2026` rejected; no time zone shifts the day (run with `TZ=Pacific/Kiritimati` and `TZ=Pacific/Pago_Pago`).
- `M1-U-3` Fuzzy categorise: exact normalised match; token-order match; longest name wins; punctuation and diacritics ignored; inactive category not suggested; no match → null.
- `M1-U-4` Inclusive day count and report aggregation functions.
- `M1-U-5` Role comparison and `requireBudgetRole` for each role and for non-members.

### End to end (Playwright)

- `M1-E-1` Sign up → lands on the dashboard of "My Budget" → add a category → add two expenses and one income → dashboard totals are correct.
- `M1-E-2` Edit an expense amount and delete another; totals update.
- `M1-E-3` Import a fixture CSV → candidates appear in the form with suggested categories → submit → expenses appear in the table.
- `M1-E-4` Compare report shows the right delta for two seeded periods.
- `M1-E-5` Create a second budget, switch to it, confirm it is empty, switch back.
- `M1-E-6` Password reset: request, follow the link captured from the test mailer, set a new password, sign in with it.
- `M1-E-7` Signed out, visiting any app page redirects to sign in.
- `M1-E-8` User B pastes the URL of user A's budget → sees a not-found page.
